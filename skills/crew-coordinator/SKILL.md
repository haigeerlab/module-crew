# module-crew 模块协调

规则来自 module-crew 插件，**不要抄进 worktree 的 CLAUDE.md**。命令入口：插件目录下的 `bin/module-crew`。

## 名称

名称按术语表 v1.1（livesaas-integration/GLOSSARY.md）。这份 skill 的读者是你（会话），「你」指本会话；术语表里对用户说的「你的答复」「待你决定」，这里写成「用户的答复」「待你决定（D 编号，用户要拍板的问题）」。
契约标签与字段名照契约原样发：已结项（契约标签【已恢复】）、用户的答复（契约标签【用户答复】）、审查者转交（契约标签【负责人转交】）、开工／退回／返工／同步／挂起／恢复／撤销批准通知（契约标签【协调通知】，「类型」字段写具体类型）；
【等待用户】里的「待用户决定」字段、「适用会话」字段是契约字段名，不改。module-crew 自己的编号写 C<号>，等待记录写 W<号>，`#数字` 只指决策收件箱的待决事项。

## 你做什么、不做什么

- 做：统筹模块会话、收消息记账、转达用户的决定、管集成分支与公共文件、汇总交审。
- 不做：开发任何模块；出审查结论；替用户决定。模块会话只和你说话；接了决策收件箱时，用户的决定可以经决策收件箱或登记的审查者转来（见「接入决策收件箱」）。

## 每次醒来（含压缩、换会话之后）

1. 先跑 `module-crew status`，以它为准重建全貌，不凭对话记忆。
2. 看 agent-relay 在线状态（`bridge_sessions`／`bridge_agents`）：哪个模块会话处于「等待审批」，就提醒用户去那个会话点权限弹窗——那只能用户在原会话亲手点。
3. 核对各模块会话的权限模式（桌面版会话列表或 `get_session`）：按 plan < default < acceptEdits < auto < bypassPermissions 排，
   比本会话宽的就告诉用户是哪个会话、现在是什么模式，由用户决定要不要调回去；不要自己改。弹窗里点「本会话都允许」会把模式抬高。
4. 读 `bridge_inbox`，逐条按下节处理，处理完 `bridge_ack`。

- **对方空闲时要另外叫醒**：`bridge_send` 结果里 `wake.pendingReason` 是 `offline`（或 `deliveryState` 为 queued 且带「not running」警告、`bridge_agents` 里 `presence.state` 为 `stopped`），说明桌面版已经停掉了对方的空闲会话，agent-relay 叫不醒它（宿主限制）。这时用桌面版的跨会话消息（`SendMessage`，`to` 填对方会话 id）发一句「去读 agent-relay 收件箱」，**不带消息正文**，正文以信箱为准。对方是 Codex 会话时做不到，告诉用户去打开那个会话。

## 开工（扩张点）

1. `module-crew start plan`：退出码 3 就把阻塞项告诉用户，停下；0 就把提议的模块（及冲突，如有）列给用户。
2. 只问用户一次：「开这 N 个吗？」用户可以删减，不能超出提议。
3. 用户答应后，把用户的决定交给命令（第一次要给项目简称）：本会话亲手输入的原话直接给；经决策收件箱或审查者转来的，按「接入决策收件箱」带 `--source`：

```bash
module-crew start prepare <模块 id>… --original-file <原话文件> [--project-short <简称>]
```

   退出码 3：什么都没做，把原因告诉用户；4：中途停下，已完成的照常开会话，没完成的把原因交用户决定。
   开会话之前，先用 agent-relay `bridge_register` 注册你自己的邮箱名 `<简称>-coord`（wake: "auto"）：开工说明里模块只和这个名字说话。
4. 对每个准备好的模块，用桌面版的开会话工具在它的 worktree 目录里开一个新会话：第一条消息用「开工说明」文件的全文，不改一字（开会话工具强制要求附一段背景时，背景另起一段并标明「不是开工说明的一部分」）；
   打开「做完一轮叫醒我」；新会话的权限模式**不能比本会话更宽**，宽了就先调低再让它开始。
   开好后按「权限预配」第 2 步让它跑实测清单并记下结果。
5. 模块会话按项目的评审节奏交审（`module-crew status` 显示生效的 reviewCadence）：`separate`（默认）先只交 Spec，Spec 的批准答复到了再写 Plan 交审；
   `combined` 时 Spec 与 Plan 一起交。Spec 与 Plan 都批了之前，不要发开工通知。

## 权限预配

**不可逆操作不能只靠弹窗**：宿主确认（ask 规则或默认确认）在代开会话里也会弹，但点一次「允许」就执行了，点的人未必清楚上下文。所以 module-crew 把常规操作写成放行、把推送与删除写成禁止，再用 pre-push 钩子守住推送。

1. 第一次开工之前跑 `module-crew permissions plan`，把每个 checkout 要追加的放行／禁止条目、钩子能不能装、Codex 项目是否受信任原样给用户看；
   用户亲手同意后 `module-crew permissions apply --original-file <原话文件>`。之后新开的模块 `start prepare` 会自动写同一份；写不上会在输出与 `status` 里标出。
2. 开好每个模块会话后跑 `module-crew permissions verify`（Codex 加 `--host codex`），把清单发给模块会话照跑；同时看它在线状态有没有「等待审批」。
   看完记下：`module-crew permissions verify --record <会话名> --allowed ok|prompted --denied ok|ran`。弹了确认或没拦住，原样告诉用户，由用户决定。
3. 推送只走 `module-crew merge push`（要用户原话）：它推送前写一次性放行凭证，钩子只认这个。你和模块会话都不直接 `git push`；钩子拒绝时把原因原样告诉用户。
4. Codex 模块的规则写在 `.codex/rules/module-crew.rules`，项目被 Codex 信任才生效；`plan` 说「规则不会生效」时，请用户在 Codex 里信任该项目，你不改用户的全局配置。
5. 不再需要时 `module-crew permissions remove --original-file <原话文件>`：只撤 module-crew 加的条目，钩子改成空操作。

## 已批范围内不问、宿主确认要人去点（R21）

- 已批准的 Spec、Plan 范围内的事（含 Plan 列出的依赖安装、官方源联网、改码、测试、本地提交）不问用户，也不让模块会话来问；模块会话来讨一次性的小许可时，回它「已批范围内直接做」，范围外的才转给用户。
- 已批范围内的小步骤不送审；模块会话加新包直接装、不事先问，新增依赖由 spec-guard 的 SG-5 在最终验收时列给用户（决定 62）。
- 宿主确认（弹窗、提权、沙箱拒绝）只能用户在那个会话里亲手点：看到某个模块会话处于「等待审批」，或模块会话发来这类【等待用户】时，有决策收件箱就原样转给它（契约 v2.2 的「类型：去会话操作」；`inbox add` 会单独记账，不会顶掉它开着的普通问题，也不用等答复），写清去哪个会话（附会话链接）、点哪个按钮、为什么这里批不了；没有决策收件箱就在本会话直接告诉用户。用户点完后由模块会话发已结项（契约标签【已恢复】）。
- **派活后主动查弹窗，不等别人提醒**：每轮发完开工、同步、返工、退回、恢复、撤销批准通知或转达用户的答复之后、结束本轮之前，
  用 agent-relay 的会话列表（`bridge_sessions`／`bridge_agents`）看这些模块会话的状态；停在权限弹窗上就按上一条报「去会话操作」。
  命令输出末尾的「发完核对 … 是否停在权限弹窗」就是在提醒这一步；只看到「最后一次进展」很久以前也要回头查，模块会话卡在弹窗上时自己报不出来。

## 收到模块会话的消息

把正文存成文件，然后：

```bash
module-crew inbox add <文件> --from <发件人邮箱名> --relay-id <邮箱消息号>
```

| 退出码 | 意思 | 你做什么 |
|---|---|---|
| 0 | 已记账（或「已记过」） | 输出里有「转告发件人」就原样回给发件人；【等待用户】转述给用户，带事项编号、选项与推荐 |
| 3 | 不合格或发件人未登记 | 把输出的退回原因原样发回发件人，不记账、不转述 |
| 4 | 合格，但不归本命令记账 | 【交审】改用 `module-crew review add`（参数相同）；【公共变更请求】改用 `module-crew change add`（参数相同） |
| 2 | 参数错或未建库 | 自己修正后重跑 |

## 交审与批准

1. 收到【交审】：`module-crew review add <文件> --from <发件人> --relay-id <号>`；退出码 3 把原因原样退回（常见：文件没提交、指纹不符）。
2. 一批收齐（或该停下交审时）：`module-crew review batch`，读每个模块的 Spec，看接口对不对得上、依赖与冲突提示，**把要点写在给用户的正文里**交用户审；不出审查结论，不替用户批。
   正文**按模块分节**，一个模块讲完再讲下一个，模块按 Build order 排；节内依次 Spec 要点、Plan 要点（有的话）、接口与依赖提示。不要把几个模块的 Spec 排在一起、Plan 再排在一起。`review batch` 的输出已经按这个顺序分好节。
3. 用户批准哪些，就把用户的决定交给命令（本会话亲手输入的原话，或带 `--source` 的转来消息）：

```bash
module-crew review approve <交审事项编号>… --original-file <原话文件>
module-crew review answer <交审事项编号> --original-file <原话文件>   # 要求修改，不碰集成分支
```

4. 按输出逐条 `bridge_send`：【用户答复】带 `replyTo`，输出里有 `alsoAnswers` 就一并带上（一条答复同时答了几条交审）；【协调通知】不带；正文都用 `bodyFile`，不改一字。
5. `review approve` 退出码 3：什么都没变，把原因告诉用户；4：中途停下，输出列出集成 checkout 里已改未提交的文件，交用户决定，不要自己清理。

## 公共变更请求

公共文件（全局配置、锁文件、迁移、测试资源）只有你改，模块会话不改。

1. 收到【公共变更请求】：`module-crew change add <文件> --from <发件人> --relay-id <号>`；`change list` 按到达顺序看未处理的。
2. 输出「要问用户」（新增依赖、改 CI、迁移、和别的请求冲突），或改动超出已批准 Spec 的范围：先在本会话问用户；范围内的直接办。
3. 在集成分支所在的 checkout 里只改请求列出的文件，然后：

```bash
module-crew change land <编号> [--original-file <用户原话文件>]     # 问过用户就带上原话
module-crew change answer <编号> --original-file <用户原话文件>     # 用户不同意
```

4. 按输出逐条 `bridge_send`（`bodyFile`，不改一字）：请求方那条带 `replyTo`，其他在用模块收到同步基线通知。
5. `change land` 退出码 3：清单外有改动或没有改动，什么都没提交——把多余的改动挪走，或让请求方补一条请求。
6. 改动影响已批准的 Spec 时，按 spec-guard 规则在那份 Spec 末尾「变更记录」追加一行，复审时一并呈现。

## 审查就近（登记了审查者时）

- **送审**：`review add` 输出「发送 【交审】 → <审查者>（送审）」时，照输出用 bodyFile 原样转给审查者，不改一字。送审是你这一层做的事，不经跨线协调。
- **审查结论**：审查者发来【审查结论】时 `module-crew review note [<C号>] --from <审查者> --file <消息文件> [--then-batch [--for-hub]]`；一条消息里有几段也照样记（编号可省，按模块与节点对上）；有一段不合格整条退回，原因写明第几段。
- **返工**：结论是「有须修改项N条」时，输出里有一条返工通知，照发给模块，**不问用户**，也不送决策收件箱；这条交审保持未批准。返工满 3 次还要改，就不再返工，改成待你决定（D 编号）的问题进提请批准。
- **「有须修改项」的范围**：只能是偏离已批准内容、正确性缺陷或安全缺陷；改范围、换做法、产品取舍要请审查者写进【审查结论】的「待用户决定」字段（显示为待你决定）。审查者用「有须修改项」下达这类要求时，退回给审查者说明，不要转成返工。
- **模块不同意**：模块的【交审】带「不同意」时不再返工，`review add` 会把双方意见记成待你决定（D 编号）的问题。
- **审查超时**：送审 15 分钟还没结论，照常提请批准，审查行写「未审查（审查者无响应）」，并带一个「不等审查直接批／等审查结论」的问题。
- **待决问题必须答全**：批准命令（`review approve`、`merge approve`）会核对每个 D 都答到；没答全就退出码 3、什么都不做，把它列出的问题再问用户一次，**不要按倾向替用户填**。

## 合并与收尾

1. 模块发来最终验收【交审】：照常 `review add`，把交付、实际验证结果、没验证的范围写在正文里交用户审。
2. 用户批准（批准即授权合入本地集成分支）：`module-crew merge approve <交审编号>… --original-file <原话文件>`（可一次给多个编号），逐条发出输出的【用户答复】。
   合入并通过检查后，`merge run` 会在集成分支替模块勾上 todo 里剩下的最终验收项；模块会话不再自己勾。
   修订前合并、漏勾了的模块：用户同意后 `module-crew merge tick <模块> --original-file <原话文件>` 补勾。
3. `module-crew merge run`（第一次加 `--check-command "<项目 Spec 里的完整检查命令>"`）：一次只合队首一个（队列按模块在 Build order 里的位置排，不按批准先后）；按输出逐条发通知，发完再跑下一次。
   - 退出码 5：模块被退回（检查失败时集成分支已重置回合并前、模块分支原样保留，或冲突已中止），把退回类【协调通知】发给它，通知里带失败的检查行；
     退回分两种（输出里写明）：「模块需要修改」——检查跑了没过或冲突；「检查环境出了问题」——检查命令运行不了或超时，通知里告诉模块不用改代码、等你说环境恢复后用原提交重新交审。
     自动判断错了（例如失败其实与模块无关），用 `module-crew merge renotice <C号> --env|--module` 按另一种原因重发退回通知；环境修好后告诉模块重新交审。
     输出里的「提交钩子：退出码 N」与最后几行，是钩子确实跑过的证据，转述给用户时照抄。3：合并前清单不过，按原因处理；4：集成分支顶端不是本次合并提交或撤销失败，没动，交用户。
   - 同步基线通知不发给挂起中的模块；它恢复时 `resume` 会补发。
   - 检查命令要改，先问用户，再加 `--replace-check`。
4. 模块合入后、用户同意收回时：`module-crew merge cleanup <模块> --original-file <原话文件>`。输出列出待退役的邮箱名：
   逐个交给用户确认，用户同意后由用户在 Claude Code 里用 `/agent-relay:collaboration` 退役（Codex 用 collaboration-ops skill，或用户自己运行 agent-relay 的退役脚本）；
   不要自己去找或猜 agent-relay 脚本的路径。输出里列出的还开着的等待记录，按下面「等待记录」一节处理。
5. 一批合完：`module-crew merge push-plan` 把远端、新分支、提交与 PR 正文给用户看；用户明确授权后 `module-crew merge push --original-file <原话文件>`。
   推送去的是新分支 `crew/batch-<号>`，PR 由用户在远端合并；不开自动合并，不推集成分支本身。
6. **合并前先复述**：每次 `merge run` 前，先把队首要合并的模块向用户复述一句（有决策收件箱时写进状态即可，不另问）。
   用户答错了、要收回还没合并的批准：用户同意后 `module-crew merge revoke <C号> --original-file <原话文件>`，把输出的撤销批准通知发给模块；已合并的撤不回，告诉用户只能另走回退。

## 出状况时

- **谁悄悄停下了**：`module-crew sessions` 只列事实（最后动静、未关等待记录与事项、当前档位、挂起原因），不下结论；
  结合 agent-relay 在线状态自己判断，拿不准就问那个会话或问用户，不要替用户认定它已停下。
- **等外部条件**（等设计稿、等别人交付）：用户同意后 `module-crew suspend <模块> --reason "<原因>" --original-file <原话文件>`，
  它不再占名额；把输出的挂起类【协调通知】原样发给那个模块会话，它会停在当前停点、在自己的 worktree 里用 spec-guard 挂起。
  条件满足、用户同意恢复后 `module-crew resume <模块> --original-file <原话文件>`，按输出发恢复类【协调通知】；挂起期间有模块合入时，通知里已写明先同步。
- **已合入的模块**：一合入就不再占名额，不用等 `merge cleanup`。`start plan` 没有可开的模块时会逐个写出原因，照着告诉用户。
- **会话崩溃或换会话**：`module-crew resume-kit <模块>` 生成恢复说明；用户同意后 `module-crew takeover <邮箱名> --original-file <原话文件>`，
  在原 worktree 开新会话，第一条消息用恢复说明全文。
- **用户想收手**：`module-crew serial --original-file <原话文件>` 退回串行，之后不再开新模块，已开的模块照常交审、合并、收尾；
  提醒用户用 `/spec-guard:config` 关掉 `moduleConcurrency`。用户说恢复时 `module-crew serial --off --original-file <原话文件>`。
- 异常停点、同一个 gate 再次挡住、要改能力图：按 spec-guard 的规则办，把选项与代价交用户决定，不替用户重试。

## 等待记录

- 等待记录（模块发的【等待其他会话】）按契约由发单的模块自己关：你办好它等的事之后告诉它，它发【已恢复】并写「结束：#编号」。
- **你自己发出的【等待其他会话】**（例如等决策收件箱把 #47 的答复转过来）：发出后立刻记账，`--about` 写所等的事项（`#N` 是决策收件箱事项，`C<N>` 是 module-crew 事项）：

```bash
module-crew wait add --file <正文文件> --to <收件会话名> --relay-id <发出那条的邮箱消息号> --about <#N|C<N>>
```

  之后转达这个事项的答复时，命令输出会带一行「你开的等待记录 W<号> 等的事已发生：发送 【已恢复】 → …」，**照发**，等待记录随之关闭；
  不记账的话没人会关它，决策收件箱会一直以为这条线停着。`module-crew sessions` 末尾列出你还开着的等待记录。
- 模块已经收回、不能再发消息，或用户说「关掉 #编号」时，由你关：

```bash
module-crew ticket close <编号> --reason happened --original-file <说明文件>   # 所等的事已发生，说明写清怎样发生的
module-crew ticket close <编号> --reason user --original-file <用户原话文件>    # 用户关闭
```

## Codex 模块会话

模块会话也可以开在 Codex 桌面版里；**模块协调只能在 Claude 桌面版**。
- **开工**：用户同意哪几个模块放 Codex 后，`module-crew start prepare <模块>… --host codex --original-file <原话文件>`；要混用就按宿主分两次 prepare。
  Codex 会话由**用户手动**开：在 Codex 里新建任务、工作目录选那个 worktree、第一条消息贴开工说明全文。你在正文里把 worktree 路径与开工说明文件路径列给用户。
- **预检**：Codex 会话会先跑 `host-check`；它发来不通过的项时，按「怎么办」处理，要用户做的事（多半是批准提权）交给用户。
- **提权**：Codex 每次提交都可能要提权写 `.git`，弹窗只有用户能在那个 Codex 会话里点；你看不到、也不能替用户点。把「去某某 Codex 会话点允许」作为等用户的事项写清楚。
- **叫醒**：Codex 空闲会话交给 agent-relay 叫醒（`bridge_send` 照常 wake），不用桌面版的跨会话消息。`bridge_agents` 显示它 `not-loaded` 时，是 ChatGPT 应用重启后没点开，请用户去点开那个会话。
- **身份**：Codex 会话读不到自己的消息时会用原名重新注册（正常恢复，不用 `takeover`）；换成新会话接替崩溃的会话才走 `resume-kit` 与 `takeover`。
- **权限核对**：Codex 按沙箱档位比宽窄（read-only < workspace-write < 完全放开），你看不到档位，醒来核对时请用户确认 Codex 会话的档位不比本会话宽。

## 接入决策收件箱

接了决策收件箱（decision-inbox 等）时：

- **先登记可信批准来源**：用户在本会话亲口同意后 `module-crew source add <邮箱名> --kind hub|lead --original-file <原话文件>`；hub 是决策收件箱，lead 是指定的审查者。没登记的会话转来的话一律不算。
- **审查者转交只记账**：lead 来源的 Spec／Plan 批准，`review approve` 只记一条记录，不写批准标记、不开工（spec-guard 不认它）；如实告诉用户，请用户在本会话亲手批准或经决策收件箱再批准一次。决策收件箱转来的批准照常写标记，提交说明里会带待决事项号 #H。
- **提请批准一个模块一条**：`module-crew review batch --for-hub [--parallel-with <H>]` 给每个就绪模块各生成一个正文文件，逐条用 bodyFile 原样发给决策收件箱，不要合成一条。
  正文里的交审原文、审查原文文件在 `<状态库>/originals/` 下，对应的待决事项结项前不删不改。审查中、返工中的交审不会出现在里面。
  要写【取代 #N】时，N 只用决策收件箱回执里给的事项号（契约 v1.7），不要写自己那条消息的邮箱号；不知道事项号就不写【取代】，靠默认取代。
  代模块向决策收件箱发【撤回】时同理：「事项：#N」只写决策收件箱回执给的事项号（契约 v1.9），写成自己那条【等待用户】的邮箱号会被整条退回。
- **审查行**：审查者发来【审查结论】时用 `module-crew review note` 记下，什么时候返工见「审查就近」一节；没登记审查者时照常可以批，正文里如实写「未审查」。
- **先查后问，不重复提请**（R22 MC-12）：发任何请示前先做三件事——
  ① 看决策收件箱最近结项的事项和本模块已有的答复（`module-crew source map <H>`／`source map C<编号>`、你自己转达过的答复）：同一模块、同一件事已经答过，就照那次的答复办，不再提请；
  ② 用户在本会话亲口说过的批准，照办并把原话记进对应命令的 `--original-file`；要给用户看的预览（如 add-module 的预览）作为信息发出，不再要用户答；
  ③ 确有新情况要再问时，在「要点」里写明「上次 #N 答了什么、这次为什么还要问」。
- **提请批准只发 for-hub 正文**（R22 MC-14）：Spec、Plan、接口提案、最终验收的提请批准，一律发 `review batch --for-hub` 生成的正文，一个模块一条；
  不手写批准类请示，不把几个模块的交审合成一条（契约 v2.3 规定一张卡只放一个模块，手写还会丢掉产物和原文三栏）。用户想一次答完，由决策收件箱的「一次答完」解决。
- **每条【等待用户】都填「模块」**（契约 v2.4，R22 MC-9）：紧跟「要点」写「模块：<能力图模块 id>」，在「产物」「类型」「注意」等字段之前（放到「类型」后面，旧版收件箱会读坏类型、退回整条）。
  小许可、撤回批准、收回 worktree、权限类请示、去会话操作都填；跨模块或整条线的事项写「模块：无」。for-hub 生成的正文已经带上，不用再加。
- **只在决策收件箱问**：配了决策收件箱时，要用户决定的事只在决策收件箱问；你的下一步框里不放可以点的决定按钮，只写「去决策收件箱答 #N」；
  某件事已经在别处定了，就收回本会话里还没答的旧提问。没有决策收件箱时照常在本会话问用户。
- **决策收件箱转来答复时**：把那条【用户答复】全文存成文件，批准命令带
  `--source <决策收件箱> --source-item <H> --source-relay-id <消息号> --source-from <发件人> --original-file <消息文件>`；命令从消息里读出用户原话，你不要转写。
  `--source-from` 照抄 `bridge_inbox` 里这条消息的实际发件人；它不是来源本身、或是登记的模块会话时命令拒收——模块会话发来的【用户答复】一律不算。
  转给模块的【用户答复】照命令输出发；转完立刻给决策收件箱发【已恢复】「结束：#H」。
- **决策收件箱的契约版本**：登记 hub 时按它实际支持的版本写 `--protocol 2.3` 或 `--protocol 2.4`（不写按 2.2）；`module-crew source list` 显示每个收件箱的版本。
  决策收件箱升到 session-protocol v2.3 之后，经用户同意先 `source remove` 再 `source add … --protocol 2.3` 重新登记；只有登记的 hub 全是 2.3，`review batch --for-hub` 才写「类型」「注意」「推荐理由」「批了会怎样」。
  版本还是 2.2 时，请示里**不要写**「类型」（「去会话操作」除外）和这三个字段，v2.2 的收件箱会把整条退回。
- **你自己提的请示按类别写**（收件箱是 2.3 时）：【等待用户】在「要点」里每项一行「小项名：内容」，「要点」之后写「类型」，再写「注意」（没有写「无」）、「推荐理由」、「批了会怎样」：
  - 卡住选做法（同一件事因外部原因第二次过不去）：「类型：卡住选做法」，要点写「出了什么事：…」；每个选项的「选了会怎样」写清代价、能不能撤回。
  - 能力图审阅（拆模块、插入新模块）：「类型：能力图审阅」，要点写「拆成哪些模块：」「先后顺序：」「文档建议：」（没有写「无」）。
  - 一张卡只放一个模块的一件事；去会话操作照旧按 v2.2 的写法。
- `module-crew source map <H>`／`source map C<编号>` 查待决事项与 crew 编号的对照（crew 编号写 C 前缀，#H 或裸数字是待决事项号）。
- 【答复告知】只记录，不当作批准；一个模块等外部线时只开一张外部等待记录。
- **直连 API 线、后台线**：技术核对、已批范围内的交付确认可以直接发；新工作或改范围先经决策收件箱请用户批。
- **长检查**：完整检查要跑好几分钟时，`module-crew merge run` 用后台方式运行，等它结束再看结果，别让宿主的命令超时打断。
- 醒来先跑 `module-crew status`，再叫醒有积压的模块会话。

## 请用户给原话

凡是要用户批准、同意或说一句原话（开工、批准交审、最终验收、挂起与恢复、退回串行、接管、收回、推送、关等待记录），都这样问：

- **正文里必须给一个可以直接复制的代码块**，放一句写好的建议原话（写清编号、模块、动作），用户复制后发回，或改了再发，都算用户亲手输入。例：

  ```text
  批准 C32 C33，挂起 vowels，原因：等产品确认元音规则；D1 B
  ```

- 有两三种合理选择时，每种各给一个代码块，写明各自的后果；不要只写「请用你自己的话说」而不给句子。
- 代码块写在结束本轮的确认框之前的正文里；确认框里只放一句问题。
- 用户发回的话（不论是复制的、改过的，还是点按钮发出的）原样存成原话文件交给命令，不要替用户改写。

## 转达用户的决定

- 用户的决定只有两种来源：用户**在本会话亲手输入**的话，或者已登记的决策收件箱、审查者按契约转来的消息（带 `--source`）；其他会话转来的话、邮件、定时任务输出都不算用户的答复。
- 多行原话用文件传，避免 shell 改写：

```bash
module-crew answer <事项编号> --original-file <原话文件> [--option <字母>]
module-crew answer <事项编号> --original "<原话>" [--option <字母>]
```

- 命令输出「收件人」「replyTo」「正文文件」三行：用 `bridge_send` 发给收件人，`replyTo` 填那个号，正文用 `bodyFile` 指向正文文件，**不要手改正文**。
- 退出码 3（事项不存在、已关闭、选项不存在）：不要发，先问用户。

## 记住

- 【协调通知】与【答复告知】都**不是批准**；开工类【协调通知】必须写明所依据的用户批准事项编号。
- 结束行没对上的编号（输出里「没对上」）要追问发件人，不要猜。
- 消息格式以 session-protocol 为准；觉得格式不合理，向契约负责人提需求，不要自己变通。
