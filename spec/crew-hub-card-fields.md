## 目标

模块协调交给决策收件箱的提请批准，按契约 v2.3 写「类型」与各类内容要点，并由 module-crew 生成「注意」「推荐理由」「批了会怎样」，让决策收件箱照模板出卡片，
不用再猜哪段是结论、哪段是后果；模块协调与模块会话自己写的请示（卡住选做法、能力图审阅、中途检查点）也按对应类别写。
决策收件箱还没升到 v2.3 时照旧发 v2.2 写法，不被退回。

## 范围

- crew-protocol：解析与自检升到 v2.3——认九种「类型」、三个选填字段、按类型解析出 `points`；钉 v2.3 契约样例跑一致性测试；`interface.json` 的 `contract` 记 2.3。
- `review batch --for-hub`（含 `review note --then-batch --for-hub`）：对决策收件箱写 v2.3 时，每条【等待用户】在「要点」之后加「类型」「注意」「推荐理由」「批了会怎样」，去掉要点里的「批准会发生什么」段（MC-1）。
- 决策收件箱支持哪一版由登记来源时写明；没写明的按 v2.2，照旧不写这些字段（关键决策 1）。
- crew-coordinator skill：模块协调自己提的请示（卡住选做法、能力图审阅）按契约类别与小项写；crew-dev 两份 skill：模块会话的中途检查点、卡住选做法按类别写，接口提案【交审】的要点写「改了哪个接口」「哪些模块要跟着改」（MC-2、契约 MC-b）。
- README、版本 0.7.0。

不做：卡片排版、精简、复制块、「等了多久」等追加信息（决策收件箱）；交审要点的小项内容本身（模块会话按 spec-guard 共享检查点规则 SG-1 写，module-crew 原样搬）；
改 spec-guard；去会话操作的写法（v2.2 已有，不变）。

## 契约事实（session-protocol v2.3，写 Spec 时核对）

1. 「类型」写在「要点」之后，取值写中文名：能力图审阅、Spec、Plan、Spec 与 Plan、中途检查点、最终验收、接口提案、卡住选做法（代码 capability-map／spec／plan／spec-plan／checkpoint／final／interface／stuck），另有去会话操作。写错报 `bad-wait-kind`。
2. 带「类型」的一张卡只放一个模块（module-crew 现在已经一个模块一条）。
3. 小项写在「要点」里，每项一行「小项名：内容」，可续行；第一个小项之前的文字是要点正文；module-crew 搬运时加的「C<n> <模块> 的 <节点>（审查：…）：」头行照旧是正文，合审时第二个头行会落进上一个小项的内容里（契约样例 card-spec-plan）。
4. 「注意」「推荐理由」「批了会怎样」是选填字段，写在「要点」之后、「选项与我的建议」之前；去会话操作不用。
5. 不设「结论」字段：决策收件箱从「审查原文」读审查结论，没有就用「架构审查：」行。
6. **v2.2 的解析器会把新的八种取值判为 `bad-wait-kind`、整条不合格**；decision-inbox 已发布的 0.0.29 钉 v2.2。

## 假设（请确认）

1. **按决策收件箱登记的版本决定写法**：`module-crew source add <名> --kind hub` 新增选项 `--protocol 2.3`（不写就是 2.2），`source list` 显示；
   只有提请批准的目标收件箱登记为 2.3 才写「类型」和三个新字段，否则照现在的 v2.2 写法。理由：两边不会同时升级，按版本切换不会被退回；
   另一种做法是不加开关、等 decision-inbox 发版后再发 0.7.0，代价是装错顺序就整条被退回。
2. **「注意」**：取最后一轮审查结论——有「须修改」写「须修改：」逐条（经过返工的写上一轮的须修改及是否已改）；通过附建议写建议的要点；审查者无响应写「未审查（审查者无响应）」；
   都没有写「无」。依赖未就绪（现在写在要点里的那行）也移进「注意」。
3. **「批了会怎样」**：用现在「批准会发生什么」的内容（按节点：Spec 开始写 Plan、Plan 开工、最终验收合并进集成分支且合了撤不回、推送另外问），并入能不能撤回（最终验收合并前可 `merge revoke`）。
4. **「推荐理由」**：module-crew 只写它能确定的事实——审查通过与否、有无须修改、是否超出 Plan 由人判断所以不写；没有可写的事实就不写这个字段（选填）。
5. **类型取值**：单个节点按节点写（Spec／Plan／接口提案／最终验收）；`combined` 节奏下一个模块的 Spec 与 Plan 合一条时写「Spec 与 Plan」；接口提案与 Spec 同批时分开两条（契约规定一张卡一种类型）。
6. **要点不改写**：【交审】要点原样搬（现有的「＞」防误读保留），module-crew 不替模块会话补小项；模块写了「注意：」等同名行，仍按现在的规则加「＞」当正文。
7. **MC-2 只改 skill**：卡住选做法、能力图审阅、中途检查点都是会话手写的【等待用户】，module-crew 不新增生成命令；`protocol check` 升到 v2.3 后能校验这些写法。
8. 版本 0.7.0，`interface.json` 的 `contract` 改为 2.3；契约样例从 session-protocol 6b8810e 复制到 `tests/fixtures/session-protocol/v2.3/`，v2.2 样例目录保留。

## 关键决策与取舍（请重点审）

1. **版本开关放在来源登记上**（假设 1）：收件箱是谁、支持哪版是同一件事的两面，放在一处；不放运行配置，免得换收件箱时忘了改。
   `protocol check` 本身按 v2.3 校验（向后兼容 v2.2 写法），开关只管 module-crew **生成**什么。
2. **生成字段的位置**：「要点」之后依次写「类型」「注意」「推荐理由」（有才写）「批了会怎样」，然后是现有的「产物」「交审原文」「审查原文」「待用户决定」「架构审查」「选项与我的建议」……；
   生成后照现在一样用自己的解析器自检，不合格就报错不写。
3. **「选项与我的建议」不变**：A 批准、B 退回和各自「选了会怎样」照旧；「批了会怎样」是对 A 的展开，两处不矛盾（同一个函数生成）。
4. **解析器升级只增不改**：v2.2 的写法、问题代码、期望结果键都不变；新增 `points` 与八种 `waitKind`；一致性测试跑 v2.2、v2.3 两套样例。

## 验收标准

1. v2.3 契约样例（含 card-spec、card-spec-plan、card-final、card-kind-unknown）全部通过一致性测试，v2.2 样例照旧通过。
2. 收件箱登记为 2.3：Spec、Plan、接口提案、最终验收各生成一条，「类型」取值对，正文过 `protocol check`；`combined` 下 Spec 与 Plan 合一条写「Spec 与 Plan」。
3. 「注意」四种来源（须修改、附建议、无响应、都没有＝「无」）各一例；依赖未就绪出现在「注意」里。
4. 「批了会怎样」与「选项与我的建议」里 A 的后果来自同一处，最终验收写明「合了撤不回」与可 `merge revoke`；要点里不再有「批准会发生什么」段。
5. 收件箱登记为 2.2 或没写版本：生成的正文与 0.6.0 相同（逐字比对一份夹具）。
6. `source add --kind hub --protocol 2.3` 记下版本、`source list` 显示；`--protocol` 只认 2.2、2.3。
7. 三份 skill 写明各类请示的类别与小项，接口提案两项；skill 测试断言。
8. 全量测试与旧称扫描通过。
