# Spec: crew-review-nearby

<!-- spec-guard: review approved f3fdafdb24ec -->

> 能力图模块 `crew-review-nearby`（第三版）。需求来源：`livesaas-integration/REQ-REVIEW-NEARBY.md`（用户决定 41–43：审查就近、决策集中；
> 批 2 暴露的问题 R4–R9）。用户 2026-10-19 在本会话确认 21 条假设（退回上限 3 次、审查超时 15 分钟、R5 用撤回窗口、交审编号前缀 C），
> 并批准插入能力图。契约写法按 module-crew 2026-10-19 给契约负责人的答复（session-protocol v2.0 对齐初稿 MC1–MC4），**标「待契约」的地方等 v2.0 定稿后核对**。

## 目标

审查提出的修改意见在协调会话这一层就改完，用户只看到需要拍板的问题：审查要求修改时协调会话直接让模块返工，不问用户；
审查里属于产品取舍的问题单独列给用户，没答到就追问；返工过程在状态里看得见。同时修掉批 2 暴露的几处问题：最终验收选项写错后果、
合并批准撤不回、交审编号和收件枢纽事项号撞号、要点被截断、合批正文太长、处理要逐条跑命令。
不配收件枢纽、不配审查者时，module-crew 照常可用。

## 范围

- **R1 审查就近**：送审（交审原样转给登记的审查会话）、「有须修改项」时自动生成返工类【协调通知】、返工轮次与上限、模块「不同意」、审查超时、返工过程在 `status`／`sessions --json`／合批里可见。
- **R2 待用户决定**：读【审查结论】的「待用户决定」，合批正文把它们和协调会话生成的问题一起列成 D1、D2…；批准时核对每个问题都答到，没答到拒收并给追问正文。
- **R3** `review note` 接受一条消息里的多段【审查结论】。
- **R4** 合批选项按节点写真实后果；节点名一律中文。
- **R5** `merge revoke` 撤回还没合并的合并批准，并通知模块。
- **R6** module-crew 自己的编号对外一律写 `C<数字>`；命令参数 `15`、`C15` 都认。
- **R7** 要点列表不截断，截断时注明共几条。
- **R8** 合批正文「要点」前面加 3–5 行摘要。
- **R9** `review note --then-batch`：记完审查结论直接生成合批正文（或说明在等谁）。
- 协调会话 skill、两份 crew-dev skill、README 补上述做法；crew-protocol 改钉契约 v2.0。

不做：收件枢纽的回执、重新 join 的回显（R10、R11，归 decision-inbox）；判断「有须修改项」的内容是否越界（靠审查者守规矩，写进 skill）；
定时器或后台轮询（超时在命令运行时判断）；改状态库文件格式（只加字段）。

## 假设（用户 2026-10-19 已确认）

1. 「要改」沿用契约的「有须修改项」，带条数写成「有须修改项N条」，「须修改」字段逐条编号（契约 v2.0 写法）。
2. 「有须修改项」只用于偏离已批准内容或正确性、安全缺陷；改范围、产品取舍写成「待用户决定」。写进 skill，代码不判断。
3. 返工用【协调通知】新类型「返工」，依据写审查编号与交审编号、带轮次，不要求用户批准事项号（待契约）。
4. 返工上限 3 次（按模块＋节点计）；第 4 次「有须修改项」不再返工，改为待用户决定的问题。
5. 模块可在【交审】里写「不同意：<审查编号>：<理由>」，文件与上一版相同；协调会话不再返工，把双方意见列成待用户决定的问题（待契约）。
6. 登记了审查会话时由 module-crew 送审：`review add` 输出一条把【交审】原样转给审查会话的发送项（待契约写明送审）。
7. 审查超时 15 分钟，在 `review batch`、`status` 运行时按送审时间判断，不开定时器。
8. `status`、`sessions --json` 显示返工轮次；进合批时附「经 N 轮审查修改」一行。
9. 登记了审查会话时，只把可交用户的交审放进合批（见关键决策 3）；没登记时和现在一样。
10. R3 由 `review note` 自己切段；任何一段不合格整条拒收。
11. R9 用 `review note --then-batch`。
12. 待决问题放在同一份【等待用户】里，「你该回」写「A 全部批准；D1 选 B」（契约 v2.0 初稿写法，【等待用户】格式不改）。
13. 没有收件枢纽时，`review batch` 列出待决问题，由协调会话直接问用户；批准时同样核对。
14. R4：最终验收的选项后果写「排进合并队列，检查通过后合并进集成分支」。
15. R5：`merge revoke` 撤回窗口；`merge run` 前协调会话先向用户复述要合并的模块；通知模块用【协调通知】「撤销批准」（待契约）。
16. R6：对外写 `C15`，状态库仍存数字；开工依据写「#41（交审 C15）」或本地批准「C40（用户在协调会话批准；交审 C15）」（待契约）。
17. R7：要点列表被截断时写「…（共 N 条，回『详情』看全文）」；没有收件枢纽时列表完整显示。
18. R8：摘要每模块一行加待决问题个数，3–5 行，只改生成的正文。
19. 三种组合都要能用：module-crew 单用、不配审查者、配收件枢纽。
20. 批准来源、0.2.2 的规则不变；冻结的 0.2.2 不受影响。
21. 版本 0.3.0，在批 2 阶段丙开始前冻结。

## 关键决策与取舍（请重点审）

1. **每条交审有一个「审查状态」，由事件推出，不另存一张表**：

   | 状态 | 含义 | 进不进合批 |
   |---|---|---|
   | `none` | 没登记审查会话 | 进，审查行「未审查」 |
   | `reviewing` | 已送审、在等结论、没超时 | 不进 |
   | `timeout` | 送审超过 15 分钟没结论 | 进，审查行「未审查（审查者无响应）」，并生成待决问题 |
   | `rework` | 收到「有须修改项」、已发返工、等模块重交 | 不进 |
   | `passed` | 通过（含附建议） | 进 |
   | `decide` | 带「待用户决定」、或返工满 3 次、或模块不同意 | 进，带待决问题 |

   重新交审（同模块同节点取代旧的）时，新交审继承返工轮次，并自动再送审。轮次 = 这个模块这个节点已发出的返工通知条数。

2. **返工通知由 `review note` 直接生成**：结论为「有须修改项N条」且轮次 < 3 时，输出一条发给模块的「返工」类【协调通知】：
   依据「审查 R-7（交审 C15）」，轮次 N+1，「要你做什么」原样列出「须修改」各条。交审保持未答，不写标记、不碰集成基线、不产生枢纽事项。
   轮次已满 3 次时不发返工，状态改为 `decide`，生成问题「审查与模块仍有分歧：A 按模块现版本批准；B 退回按审查意见改」，并排写出最后一次审查意见。

3. **待决问题的三种来源，统一编号 D1、D2…，各自挂在一条交审上**：
   - 审查者的「待用户决定」（原样带选项与倾向）；
   - 协调会话生成的：返工满 3 次、模块不同意（选项「A 按模块现版本批准；B 退回按审查意见改」）、审查超时（选项「A 不等审查直接批；B 等审查结论」）。

   合批正文里 D 编号按这份正文重新连续编号，对照（D 号 → 交审号、来源、选项）记在正文记录里，批准时用它核对。

4. **批准时按待决问题的答案分三路**（`review approve` 与 `merge approve` 都适用）：
   - 每个挂在本次交审上的 D 都必须答到（从用户原话里认「D<k> 选 <字母>」，全角半角都认），缺任何一个就退出码 3、什么都不写，
     输出追问正文：有收件枢纽时是一条【等待用户】（只问没答到的 D，带【取代 #H】由协调会话决定用不用），没有时是一段让协调会话直接问用户的话；
   - 协调会话生成的问题按答案处理：选「按现版本批准／不等审查」的交审照常批准；选「退回按审查意见改」的交审按 `review answer` 关掉并把用户原话转给模块；选「等审查结论」的交审不动、保持未答；
   - 审查者的问题不改变批准与否，答案随【用户答复】原话送到模块。

5. **送审是一条发送项，不是 agent-relay 调用**：module-crew 不直接发消息（与现在一致），`review add` 的输出多一行「发送 【交审】 → <审查会话>（送审）」，
   正文文件是那条交审原文；协调会话照发。送审时间记在交审事项上，用于超时判断。登记了多个审查会话（lead）时发给每一个，任一给出结论就按它处理。

6. **R6 只改「对外的写法」**：状态库、事件、`--json` 的数字字段不变；文字输出、生成的消息正文、提交说明里 module-crew 的编号写 `C<数字>`；
   收件枢纽事项号仍写 `#数字`。命令参数接受 `15` 与 `C15`。`--json` 另加字符串字段 `ref`（如 `"C15"`），原有数字字段不变。

7. **R5 撤回窗口**：`merge revoke <C号> --original-file <原话>` 只撤 `open` 的合并批准（还没进 `merge run`）；关为 `revoked`，
   输出给模块的「撤销批准」类【协调通知】（依据：被撤的批准号与用户撤回那条答复的编号）。已在合并或已合并的，退出码 3，告诉用户只能另走回退。
   协调会话 skill 写明：每次 `merge run` 前先把队首模块向用户复述一句（有收件枢纽时不另问，复述写进状态即可）。

8. **R7、R8 只改生成的正文**：
   - 要点每条最多取 3 行；若第 3 行之后列表还没完，写「…（共 N 条，回『详情』看全文）」；`review batch`（给协调会话看的文字输出）不截断。
   - 摘要放在「要点：」下第一段：每个模块一行「<模块>：<节点…>（<审查状态>）」，最后一行「待你决定的问题：N 个」；超过 4 个模块时合成「另有 K 个模块…」，总共不超过 5 行。摘要之后空一行再接现在的分模块明细。

9. **R4**：选项「推荐 A：全部批准」的「选了会怎样」按本批节点拼：有 Spec／Plan 写「记评审标记，Spec 与 Plan 都批了的模块开工」；有最终验收写「排进合并队列，检查通过后合并进集成分支」；两者都有就都写。`NODE_NAME` 补「最终验收」，英文代码不再出现在正文里。

10. **只读出口只加字段**：`sessions --json` 每行加 `"review": {"state": "reviewing"|"rework", "round": N}`，不在这两个状态时为 `null`；`schemaVersion` 仍为 1。（decision-inbox 2026-10-19 提出用这个字段显示「返工中（审查第 N 轮）」。）

## 接口约定

```bash
bin/module-crew review add <文件> --from <邮箱名> --relay-id <M>          # 多输出送审发送项；认「不同意：」
bin/module-crew review note <C号> --from <审查会话> --file <消息> [--then-batch [--for-hub]]   # 多段；返工通知
bin/module-crew review batch [--for-hub] [--json]                          # 审查状态、待决问题、摘要
bin/module-crew review approve <C号>… (--original … | --source …)          # 核对 D 答案、分三路
bin/module-crew merge approve <C号>… (…)                                    # 同上
bin/module-crew merge revoke <C号> (--original <原话> | --original-file <文件> | --source …)
bin/module-crew status / sessions --json                                    # 返工轮次
```

- `review note`：`0` 记下（可能带返工发送项）；`3` 发件人未登记、任一段不合格（写明第几段）、对不上交审。
- `review approve`／`merge approve`：新增退出码 3 的原因「待决问题没答全：D2、D3」，输出追问正文路径。
- `merge revoke`：`0` 已撤回并给出通知；`3` 批准不存在、已在合并或已合并、没有原话。
- `review batch --json`：每条加 `ref`、`reviewState`、`round`、`decisions`（`[{id, source, question, options, lean}]`）；顶层加 `summary`（摘要各行）。

## 测试策略

- 夹具：登记一个审查会话（lead）跑完整返工循环：交审 → 送审发送项 → 「有须修改项2条」→ 返工通知（轮次 1）→ 重交 → 再送审 → 通过 → 进合批；中途收件枢纽正文里不出现这条交审。
- 返工满 3 次、模块不同意、超时（改送审时间模拟）各生成一个待决问题；三种答案分别走批准、退回、保持未答。
- 待决问题没答全拒收、什么都不写、给追问正文；答全时原话原样进【用户答复】。
- 三种组合各跑一遍：不登记来源与审查会话（单用）、只登记收件枢纽（不配审查者）、两者都登记。
- 多段审查结论：两段都合格逐段记；第二段不合格整条不记，原因写「第 2 段」。
- `merge revoke`：open 时撤回并出通知；已合并时退出码 3。
- C 编号：命令参数两种写法；生成的消息正文与提交说明不再出现 module-crew 的「#数字」；`--json` 数字字段不变。
- 生成的消息全部过契约 v2.0 的 `protocol.parse`；改钉 v2.0 样例跑一致性测试。

## 边界

- **总是**：返工不推进任何东西（不写标记、不碰集成基线、不产生枢纽事项）；批准仍只认用户亲手或收件枢纽转来的答复；待决问题没答全不执行。
- **先问**：改返工上限或超时时长；让审查结论直接批准；把「有须修改项」的内容判定做进代码。
- **从不**：替用户回答待决问题、按倾向默认；用返工通知代替用户的退回决定；撤回已合并的批准。

## 验收标准

1. 登记审查会话时，`review add` 输出送审发送项（正文为交审原文），交审状态 `reviewing`，不进合批。
2. `review note` 收「有须修改项2条」：输出返工类【协调通知】（依据含审查编号与交审 C 号，轮次 1，「要你做什么」含两条），交审仍未答、集成分支不变、没有枢纽相关发送项；状态 `rework`。
3. 模块重交：新交审继承轮次、自动送审；再审通过后进合批，合批正文附「经 1 轮审查修改」，且不含已改掉的意见。
4. 第 4 次「有须修改项」不发返工，生成待决问题；【交审】带「不同意」时同样生成待决问题，且文件与上一版不同则拒收。
5. 送审超过 15 分钟没结论：合批照收，审查行「未审查（审查者无响应）」，并带「不等审查／等审查」问题。
6. 【审查结论】的「待用户决定」进合批正文，编号 D1…，带选项与倾向；只是建议的仍按「附建议」显示。
7. 批准时待决问题没答全：退出码 3、状态库与 git 不变、输出追问正文；答全时按关键决策 4 分三路，原话原样进【用户答复】。
8. 没有收件枢纽：`review batch` 列出待决问题；用户在协调会话亲手答复时同样核对。
9. 一条消息两段【审查结论】：都合格时逐段记；有一段不合格整条拒收并写明第几段。
10. `review note --then-batch --for-hub`：没有在等的审查时直接输出合批正文路径；有时列出在等谁、不生成正文。
11. 合批含最终验收时，选项后果写合并进集成分支；正文里没有 `final` 等英文节点代码。
12. `merge revoke`：open 的合并批准关为 `revoked` 并输出「撤销批准」通知；已合并或在合并中退出码 3。
13. 对外文字与生成的消息里 module-crew 编号写 `C<数字>`，命令参数 `15`、`C15` 都认；开工依据按假设 16 写；`--json` 原数字字段不变并加 `ref`。
14. 合批要点的列表在第 3 行后被截断时写「…（共 N 条，回『详情』看全文）」；`review batch` 文字输出不截断。
15. 合批正文「要点」先给不超过 5 行的摘要（每模块一行 + 待决问题个数）。
16. `status` 与 `sessions --json` 显示返工轮次（`review` 字段），`schemaVersion` 仍为 1。
17. 不登记审查会话、不登记收件枢纽时，现有测试全部通过（行为不变，除 C 编号与 R4、R7、R8 的正文写法）。
18. 协调会话 skill、两份 crew-dev skill 写明：送审与返工、「有须修改项」的使用范围、「不同意」、待决问题必须答全、`merge revoke` 与合并前复述；全量测试通过。
