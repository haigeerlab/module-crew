## 目标

审查提出的修改意见在模块协调这一层就改完，用户只看到需要拍板的事：审查要求修改时模块协调直接让模块返工，不问用户；
审查里属于产品取舍的问题单独列给用户，没答到就追问；要用户批准的内容原样给全文，一次一个模块，推荐放最后；
模块按项目的评审节奏交审；最终验收按验收标准逐条给证据。同时修掉批 2 暴露的问题：最终验收选项写错后果、合并批准撤不回、
交审编号和决策收件箱事项号撞号、处理要逐条跑命令。不配决策收件箱、不配审查者时，module-crew 照常可用。

## 范围

- **R1 审查就近**：送审、「有须修改项N条」时自动生成返工通知、返工轮次与上限、模块「不同意」、审查超时、返工过程在 `status`／`sessions --json` 与提请批准里可见。
- **R2 待用户决定**：读【审查结论】的「待用户决定」，和模块协调生成的问题一起写进提请批准的「待用户决定」字段（D1…）；批准时每个 D 都要答到，没答到拒收并给追问正文。
- **R3** `review note` 接受一条消息里的多段【审查结论】。
- **R4** 选项后果按节点写真实后果；节点名一律中文。
- **R5** `merge revoke` 撤回还没合并的合并批准，并发撤销批准通知。
- **R6** module-crew 自己的编号对外一律写 `C<数字>`；命令参数 `15`、`C15` 都认。
- **R9** `review note --then-batch`：记完审查结论直接生成提请批准正文（或说明在等谁）。
- **R12 原样展示**：提请批准带「产物」「交审原文」「审查原文」与「批准会发生什么」，要点不截断、不摘要；一个模块一项。
- **R13 评审节奏**：`start prepare` 读项目 `reviewCadence`，开工说明与提请批准按 `separate`／`combined` 写。
- **R15 只在一处问**：skill 写明有决策收件箱时决定只在那里问，会话里不放可点的决定按钮。
- **R17 按证据审**：最终验收【交审】必须有「验收标准与证据」一节，提请批准把它放在要点最前。
- crew-protocol 改钉契约 v2.1；协调会话 skill、两份 crew-dev skill、README 补上述做法。新写、重写的正文用术语表 v1.1 的名称。

不做：停滞检测出口（R14）、宿主权限预配（R16），放下一版；决策收件箱的回执与重新 join 回显（R10、R11）、详情展开与原样展示的界面，归 decision-inbox；
判断「有须修改项」的内容是否越界、证据是否充分（写进 skill，代码不判断）；定时器或后台轮询；改状态库文件格式（只加字段与正文文件）；
README 与旧文字的全面改名（下一版）。

## 关键决策与取舍（请重点审）

1. **每条交审有一个「审查状态」，由记录与事件推出，不另存表**：

   | 状态 | 含义 | 提请批准 |
   |---|---|---|
   | `none` | 没登记审查者 | 收，审查行「未审查」 |
   | `reviewing` | 已送审、在等结论、没超时 | 不收 |
   | `timeout` | 送审超过 15 分钟没结论 | 收，审查行「未审查（审查者无响应）」，并生成待决问题 |
   | `rework` | 收到「有须修改项」、已发返工、等模块重交 | 不收 |
   | `passed` | 通过（含附建议） | 收 |
   | `decide` | 带「待用户决定」、返工满 3 次、或模块不同意 | 收，带待决问题 |

   重交（同模块同节点取代旧的）时继承返工轮次并自动再送审。轮次 = 这个模块这个节点已发出的返工通知条数。

2. **返工通知由 `review note` 直接生成**：「有须修改项N条」且轮次 < 3 时，输出发给模块的返工通知：依据「审查 R-7（交审 C15）」，轮次 N+1，
   「要你做什么」原样列出「须修改」各条。交审保持未答，不写标记、不碰集成分支、不产生待决事项。轮次满 3 次时不发返工，改为待决问题。

3. **待决问题三种来源，挂在交审上**：审查者的「待用户决定」（原样带选项、倾向）；模块协调生成的——返工满 3 次、模块不同意（「A 按模块现版本批准；B 退回按审查意见改」）、
   审查超时（「A 不等审查直接批；B 等审查结论」）。每条提请批准里从 D1 起连续编号，对照（D 号 → 交审号、来源、选项）记在提请批准记录里。

4. **批准时按待决问题分三路**（`review approve` 与 `merge approve` 都适用）：本次交审挂的每个 D 都必须答到，缺任何一个就退出码 3、什么都不写，输出追问正文
   （有决策收件箱时是一条只问缺的 D 的【等待用户】，没有时是给模块协调直接问用户的一段话）；生成的问题按答案处理——「按现版本批准／不等审查」照常批准，
   「退回按审查意见改」按 `review answer` 关掉并把用户原话转给模块，「等审查结论」不动；审查者的问题不影响批准与否，答案随【用户答复】原话送到模块。

5. **一个模块一项（决定 47）**：`review batch --for-hub` 按 Build order 给每个有就绪交审的模块各写一条【等待用户】；`separate` 时一项只含一个节点，
   `combined` 时同一模块就绪的 Spec 与 Plan 放在同一项。输出逐条列出正文文件。几个模块同时就绪就是几条，不合成一条。

6. **原样展示（R12）**：每条【等待用户】按契约 v2.1 写：
   - 「要点」：R17 的「验收标准与证据」（最终验收时）在最前；交审「要点」原样全文，不截断；重交时附上次「须修改」原文；最后一段「批准会发生什么」（授权什么、不授权什么、能不能撤回）。
   - 「产物」：交审文件每个一行「<模块 worktree 绝对路径>/<相对路径> ＠ <交审提交>」，重交加「（上一版 <旧提交>）」；最终验收写改动文件。
   - 「交审原文」「审查原文」：模块协调把【交审】与最后一份【审查结论】原文一字不改写进 `<状态库>/originals/C<号>-submission.txt`、`C<号>-review-R<号>.txt`，写「路径 sha256:指纹」；状态库不删文件，保留到结项。
   - 「待用户决定」「架构审查」「选项与我的建议」「你该回」放在最后。没有决策收件箱时 `review batch` 文字输出同样给全文与路径。

7. **评审节奏（R13）**：`start prepare` 读项目 `.agent/config.json` 的 `reviewCadence`（spec-guard 项目配置，只读，取值 `separate`／`combined`），记入运行配置；
   开工说明的「这一步只做」按它写。`separate` 下 Spec 批准时不发开工通知（照旧要 Spec 与 Plan 都批了才开工），模块收到 Spec 的批准答复就写 Plan 交审——crew-dev 写明这一条。

8. **送审是一条发送项**：module-crew 不直接发消息，`review add` 输出「发送 【交审】 → <审查者>（送审）」，正文文件是交审原文；登记了多个审查者时发给每一个。

9. **R6 只改对外写法**：状态库、事件、`--json` 的数字字段不变；文字输出、生成的消息、提交说明里写 `C<数字>`；决策收件箱事项号仍写 `#数字`；`--json` 另加 `ref`。

10. **R5 撤回窗口**：`merge revoke <C号> --original…` 只撤 `open` 的合并批准；关为 `revoked`，输出撤销批准通知（依据：被撤的批准号与用户撤回那条答复的编号）；已在合并或已合并退出码 3。

11. **只读出口只加字段**：`sessions --json` 每行加 `"review": {"state": "reviewing"|"rework", "round": N}`，其余为 `null`；`schemaVersion` 仍为 1。

## 接口约定

```bash
bin/module-crew review add <文件> --from <邮箱名> --relay-id <M>          # 送审发送项；认「不同意」；最终验收查「验收标准与证据」
bin/module-crew review note [<C号>] --from <审查者> --file <消息> [--then-batch [--for-hub]]   # 多段；返工通知
bin/module-crew review batch [--for-hub] [--json]                          # 审查状态、待决问题；--for-hub 一个模块一条
bin/module-crew review approve <C号>… (--original … | --source …)          # 核对 D 答案、分三路
bin/module-crew merge approve <C号>… (…)                                    # 同上
bin/module-crew merge revoke <C号> (--original <原话> | --original-file <文件> | --source …)
bin/module-crew start prepare …                                              # 读 reviewCadence
bin/module-crew status / sessions --json                                    # 返工轮次、生效的 reviewCadence
```

- `review add`：`3` 新增「最终验收缺『验收标准与证据』一节」「不同意时文件与上一版不同」。
- `review note`：`0` 记下（可能带返工发送项）；`3` 审查者未登记、任一段不合格（写明第几段）、对不上交审。
- `review batch --for-hub`：每个就绪模块输出一个正文文件路径；没有就绪的退出码 3。
- `review approve`／`merge approve`：新增退出码 3 的原因「待决问题没答全：D2、D3」，输出追问正文路径。
- `merge revoke`：`0` 已撤回并给出通知；`3` 批准不存在、已在合并或已合并、没有原话。
- `review batch --json`：每条加 `ref`、`reviewState`、`round`、`ready`、`decisions`。

## 测试策略

- 完整返工循环：交审 → 送审 → 「有须修改项2条」→ 返工通知（轮次 1）→ 重交 → 再送审 → 通过 → 提请批准；中途不生成提请批准。
- 返工满 3 次、模块不同意、超时各生成一个待决问题；三种答案分别走批准、退回、保持未答。待决问题没答全拒收、什么都不写、给追问正文。
- 两个模块同时就绪：生成两条【等待用户】；每条的产物、交审原文、审查原文文件存在且指纹对；要点与交审原文逐字一致（不截断）。
- `separate` 与 `combined` 各一次：开工说明的「这一步只做」、提请批准的分项。读不到配置按 `separate`。
- 最终验收缺「验收标准与证据」拒收；有时这一节排在要点最前。
- 三种组合各跑一遍：单用、不配审查者、两者都配。多段审查结论、`merge revoke`、C 编号同前。
- 生成的消息全部过契约 v2.1 的 `protocol.parse`；改钉 v2.1 样例跑一致性测试。

## 边界

- **总是**：返工不推进任何东西；批准仍只认用户亲手或决策收件箱转来的答复；待决问题没答全不执行；原文文件写入后不改不删。
- **先问**：改返工上限或超时时长；让审查结论直接批准；把「有须修改项」或证据的判定做进代码。
- **从不**：替用户回答待决问题、按倾向默认；用返工通知代替用户的退回决定；撤回已合并的批准；截断或摘要要批准的原文。

## 验收标准

1. 登记审查者时，`review add` 输出送审发送项（正文为交审原文），交审状态 `reviewing`，不进提请批准。
2. `review note` 收「有须修改项2条」：输出返工通知（依据含审查编号与交审 C 号，轮次 1，含两条），交审仍未答、集成分支不变、没有提请批准；状态 `rework`。
3. 模块重交：继承轮次、自动送审；再审通过后提请批准，产物行带「（上一版 旧提交）」，要点附上次「须修改」原文。
4. 第 4 次「有须修改项」不发返工，生成待决问题；【交审】带「不同意」时同样生成待决问题，文件与上一版不同则拒收。
5. 送审超过 15 分钟没结论：照常提请批准，审查行「未审查（审查者无响应）」，并带「不等审查／等审查」问题。
6. 【审查结论】的「待用户决定」进提请批准的「待用户决定」字段（D1…，带选项与倾向）；只是建议的仍按「附建议」显示。
7. 批准时待决问题没答全：退出码 3、状态库与 git 不变、输出追问正文；答全时按关键决策 4 分三路，原话原样进【用户答复】。
8. 没有决策收件箱：`review batch` 列出待决问题与原样内容；用户在模块协调亲手答复时同样核对。
9. 一条消息两段【审查结论】：都合格逐段记；有一段不合格整条拒收并写明第几段。
10. `review note --then-batch --for-hub`：没有在等的审查时直接输出提请批准正文路径；有时列出在等谁、不生成正文。
11. 含最终验收的提请批准，选项后果写合并进集成分支；正文里没有 `final` 等英文节点代码。
12. `merge revoke`：open 的合并批准关为 `revoked` 并输出撤销批准通知；已合并或在合并中退出码 3。
