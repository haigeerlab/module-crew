## 目标

把阶段丙里让用户多答、多点弹窗、认不出模块的几处 module-crew 缺口补上：已交最终验收的模块不再被同步通知打断而让批准作废；同一模块只留一个有效的合并批准；
模块会话在自己 worktree 里写文件不弹窗；已经答过、已经亲口批准过的事不再提请；给决策收件箱的请示都带「模块」（契约 v2.4）；提请批准只发 for-hub 生成的正文。

   summary 在 33898a3 交了最终验收后收到同步通知、合入 main，HEAD 变了，`merge run` 的合并前清单因「交审之后又有提交」拒绝，只好重交、再问用户一次（REHEARSAL-LOG #32～#34）。

3. **MC-13**：模块 worktree 的 `.claude/settings.local.json` 没有 Edit 规则，默认权限模式下第一次 Write 就弹窗（REHEARSAL-LOG 19:07 #39）。

4. **MC-12**：#35 按 B「留着」结项后几分钟，模块协调又提请 #36 问同一件事；#37 是用户已在模块协调里亲口批准加两行后，又就 add-module 预览提请一次。两张都是模块协调手写的请示，不经 module-crew 命令。
5. **MC-14**：#40 是模块协调手写的跨模块合问（REHEARSAL-LOG 19:12「这次由模块协调手写要点」），不是 for-hub 生成的；for-hub 一个模块一条，每条都带产物、交审原文、审查原文。
6. **MC-9**：契约 SP-3 已定稿为 session-protocol **v2.4**（提交 495b475，事项 JWPFQEG，用户 2026-10-20 批准）：【等待用户】选填「模块：<能力图模块 id>」，跨模块或整条线写「无」，不校验 id；

## 关键决策与取舍（请重点审）

1. **MC-10 跳过的判定**：模块有 `kind == review`、`node == final`、`state == open` 的交审就跳过（审查中、返工中、等批都算）；合并批准开着照旧跳过。被跳过的模块不补发：
   它的最终验收要么合并（之后收到收尾通知），要么被退回或重交（退回通知原本就要求先同步；用户答 B 时 crew-dev skill 要求改完先 `module-crew sync`）。`change land` 同样跳过。
2. **MC-11**：`merge approve`（含 `approve_many`）写新批准的同一事务里，把同模块其他开着的合并批准关掉（`closedReason: superseded`、`supersededBy: <新批准号>`），输出「合并批准 C<旧> 被 C<新> 取代」。
3. **MC-13 规则写法**：allow `Edit(//<worktree>/**)`，deny `Edit(//<worktree>/.claude/**)`（deny 先于 allow）。worktree 路径取会话登记里的绝对路径，去掉开头的 `/` 再加 `//`。
   `remove` 照旧只撤自己写的条目；`plan` 的「会被盖过」检查对新条目同样生效。
4. **MC-12 skill 写法**：提请前 ①看决策收件箱最近结项的事项和本模块已有的答复（`module-crew source map`、协调会话自己的记录），同一模块、同一件事已答过就照答复办；
   ②用户在本会话亲口说过的批准，照办并记下原话，要展示的预览作为信息发出、不再要用户答；③真有新情况要再问时，在请示里写明「上次 #N 答了什么、这次为什么还要问」。
5. **MC-14 skill 写法**：提请批准只发 `review batch --for-hub` 生成的正文，一个模块一条；不手写批准类请示，不把几个模块合成一条；用户想一次答完由决策收件箱的「一次答完」解决。
6. **MC-9 一律写「模块」、不加开关**：契约 v2.4 实测 v2.2、v2.3 解析器都照收带「模块」的消息，开关挡不住任何退回；代价是 v2.3 的收件箱会把这一行算进要点最后一个小项（显示上多一行，不出错），
   以及 0.7.0 的「v2.2 写法逐字不变」回归夹具要随之更新（只多「模块：」一行）。for-hub 每条只放一个模块，所以填该模块 id；手写的线级事项写「无」。

## 验收标准

1. 重放 summary 场景：模块交了最终验收后，另一模块合并成功，`merge run` 的同步通知不发给它；它的最终验收照常合并，用户只被问 1 次。`change land` 同样不发给它。
2. 同一模块已有开着的合并批准时再 `merge approve`：旧批准关闭为 superseded、记新批准号、`merge queue` 只剩新的；不同模块互不影响。
3. 0.6.0 的重交审作废与本条一起重放：任何顺序下合并队列里同一模块只有一个开着的批准。
4. `permissions plan／apply` 对模块 worktree 列出并写入 `Edit(//<wt>/**)` 与禁止 `Edit(//<wt>/.claude/**)`，集成 checkout 不写；`remove` 能撤；`start prepare` 新建 worktree 跟随写。
5. 实地验证：默认权限模式的模块会话在 worktree 内 Write、Edit 不弹窗；编辑 `.claude/settings.local.json` 被拒。做不了记「宿主未验证」并写原因。
6. crew-coordinator skill 写明 MC-12 的三步与 MC-14 的规定；两份 crew-dev skill 写明退回或答 B 后先 sync 再重交；skill 测试断言。
7. MC-9：v2.4 样例（module-id、module-none、module-with-kind）与 v2.2、v2.3 样例全部通过一致性测试；for-hub 每条都紧跟「要点」带正确的「模块」，正文过 `protocol check`；
   v2.2 回归夹具更新后与旧版只差「模块：」一行；skill 写明 #34、#35、#61～#63 这类手写请示（小许可、撤回批准、收回 worktree、权限类）填「模块」，线级写「无」。
8. 全量测试与旧称扫描通过。
