# Spec: crew-contract-v26

> 能力图模块 `crew-contract-v26`（第七版第 3 个）。需求来源：`docs/requirements-record.md` 第 16 节第 5～9 条及第 6 项的补充（用户 2026-10-22 确认）；契约 session-protocol v2.6（提交 92309e7，CHANGELOG「v2.6」一条）。
> 依赖 `crew-protocol`（解析与生成）、`crew-hub-bridge`（决策收件箱登记与转达）、`crew-hub-card-fields`（审批卡片小项）。标「新」的是写 Spec 时补的实现取舍，请重点审。

## 目标

把 module-crew 钉到契约 v2.6：认得出、也会写 C 待定编号和新的小项名，给用户的答复块一块只答一件事；
只往登记为 v2.6 及以上的决策收件箱发带 C 待定编号的卡，低于 v2.6 照旧用 D。钉住后回报契约负责人。

## 范围

**范围内**

1. 钉住 v2.6：契约仓库 `fixtures/` 复制到 `tests/fixtures/session-protocol/v2.6`（连同 SHA256SUMS），解析测试按 v2.6 跑全部样例（含新增 5 份），已有版本的样例照旧。`CONTRACT_VERSION` 改为 2.6。
2. 解析：
   - 「待用户决定」的条目编号认 `C<交审号>-<序号>`（整体一个编号），`bad-decision-item`、`duplicate-decision` 冒号后可接它；
   - 用户答复里认「C15-1 B」这类待定编号的答法（和「D1 B」同样的写法与分隔）；
   - 审批卡的小项名加 v2.6 新名：Spec 的「边界」「未决问题」，Plan 的「架构决定」「未决问题」；旧名照认，新旧名在 `points` 里各记各的；
   - 【交审】的「要点」按节点解析小项，另给 `points`。
3. 生成：
   - 提请批准时给用户看的待定问题编成 `C<交审号>-<序号>`（审查者写的 D 由模块协调改编）；决策收件箱登记低于 v2.6 时照旧编 D；没有决策收件箱时用 C；
   - 答复块（for-hub 正文的「你该回」与会话里给用户的复制块）：一块只答一件事，「<编号> <字母>」，待定问题接「；<待定编号> <字母>」；另一种答法单独一块；推翻或重申已定决定单独一块；不出占位块；
   - 给用户看的字段一件事一个号：同一份交审从提请批准、批准到合入都用交审号，不出现批准记录号、合并批准号等内部号；
   - module-crew 自己写的审批卡（Spec、Plan 两类）用新小项名。
4. 改名：最终验收「要点」里的「验收标准与证据」改为「验收结果」（按验收标准逐条写结果和证据）；`review add` 新旧两个名都认，crew-dev skill（Claude 与 Codex 两版）改写新名。
5. 决策收件箱登记：`source add --protocol` 可选 2.6；`source list` 显示登记版本。
6. 钉住后向契约负责人（local_e1431df1）回报钉住的版本与实现情况。

**范围外**

- 改本机任何项目的登记（di-p0-hub 改登记为 2.6 在第七版发版后做，写那个项目的状态库，到时先问用户）。
- 最终验收的呈现格式（文档表、代码文件表等）与三种模板：归 crew-review-display。
- 改审查者的写法：审查者仍写 D。

## 假设

1. 决策收件箱 0.0.37 认 C 待定编号与答法、新小项名（契约 CHANGELOG 写明）；module-crew 只按登记的契约版本判断，不探测收件箱实际版本。
2. 「交审号」就是 module-crew 交审事项的 C 编号；一份交审带的待定问题按出现顺序编序号，从 1 起。
3. 已经发出、用 D 编号的待定问题不改编；本模块只影响之后生成的正文。
4. 契约 v2.6 只增不改，v2.2～v2.5 样例的解析结果不变。

## 关键决策与取舍（请重点审）

1. **（新）待定编号跟交审走，不再全批连续编号**：现在 D1、D2… 在一次提请里跨模块连续编；改为每份交审各自 `C<交审号>-1`、`-2`…，换批次、重发都不变号，用户在不同消息里看到的是同一个号。
   低于 v2.6 的收件箱照旧走 D 连续编号的老路（两套编号由同一张对照表生成，答复时按出现过的那套认）。
2. **（新）按登记版本切换，不按收件箱实际版本**：只看 `source list` 里登记的 `--protocol`；登记 2.6 以下一律 D，和契约的升级顺序一致。没有决策收件箱、在会话里直接问用户时用 C。
3. **答复块的写法放进生成器**：for-hub 正文与会话复制块都由同一个函数按「一块一件事」生成，测试只核对它的输出；契约不判定答复块，module-crew 自己的测试守住写法。
4. **内部号不进给用户看的字段**：for-hub 正文、【等待用户】、【用户答复】里提到的已批准、已合入一律写交审号；命令行给模块协调看的输出照旧带内部号（模块协调要用它运行命令）。
5. **改名两头认**：`review add` 认「验收结果」与「验收标准与证据」任一个标题，skill 只教新名；不报旧名为错，免得已开工的模块会话被拒收。

## 接口约定

- `source add --protocol 2.6`；`PROTOCOLS` 增加 `"2.6"`。
- 解析结果：`decisions[].id` 可为 `C15-1`；【交审】解析结果增加 `points`（按节点的小项列表，同 wait-user 的写法）。
- 退出码不变。

## 测试策略

- 夹具：v2.6 全部样例按 JSON 期望解析一致（含新增 5 份，`decision-cnum-bad` 报 `bad-decision-item:C15-1`）；v2.2～v2.5 照旧；SHA256SUMS 与契约仓库一致。
- 编号：同一批里两份交审各带待定问题 → 登记 2.6 的收件箱得到 `C<号>-1`…；登记 2.5 的得到 D 连续编号；没有收件箱得到 C；答复「C15 A；C15-1 B」与「D1 B」各自被认。
- 答复块：两件事两块；带待定问题的接在同一块；另一种答法单独一块；没有占位块。
- 内部号：for-hub 正文与【用户答复】里不出现批准记录号、合并批准号。
- 改名：最终验收用「验收结果」或旧名都收；两个都缺被拒；skill 里只剩新名。
- 回归：全量测试通过。

## 边界

- **始终**：按登记版本切换编号；旧名照认；协议模块不做 I/O。
- **先问**：改本机项目的决策收件箱登记；改审查者的 D 写法；对低于 v2.6 的收件箱发 C 编号。
- **绝不**：往登记低于 v2.6 的收件箱发带 C 待定编号的卡；把内部号写进给用户看的字段。

## 验收标准

1. `tests/fixtures/session-protocol/v2.6` 与契约仓库 92309e7 的 `fixtures/` 逐文件一致；v2.6 全部样例解析与期望一致，v2.2～v2.5 照旧；`CONTRACT_VERSION` 为 2.6。
2. 「待用户决定」认 `C<交审号>-<序号>`，反例报 `bad-decision-item:C15-1`、重复报 `duplicate-decision:C…`；用户答复里「C15-1 B」被认。
3. Spec、Plan 卡认新小项名「边界」「未决问题」「架构决定」，旧名照认，`points` 各记各的；【交审】解析结果有 `points`。
4. 决策收件箱登记 2.6 时提请批准的待定问题写 `C<交审号>-<序号>`，登记低于 2.6 时写 D，没有收件箱时写 C；答复按出现过的那套编号认。
5. 答复块一块一件事、待定问题接在同一块、另一种答法单独一块、没有占位块；给用户看的字段只用交审号。
6. 最终验收「验收结果」与旧名「验收标准与证据」都收、都缺被拒；两份 crew-dev skill 与 crew-coordinator skill 用新名。
7. `source add --protocol 2.6` 可用，`source list` 显示版本；全量测试通过；钉住后已向契约负责人回报。
