# 多模块并行开发 · 需求记录（定稿草案）

> 状态：第 2 关已获用户批准（2026-10-18，含 11 条假设）；第 3 关已下发 ①spec-guard 负责人、②decision-inbox 负责人；契约 v1.0 已迁移（session-protocol 7585be8）；③已开 module-crew 开发会话（local_dbe419ad） · 第 1 关结论于 2026-10-17～18 逐项确认
> 读者：开发 spec-guard 规划层的会话、开发 module-crew 的会话、session-protocol 的维护者。不看讨论记录也应能读懂。
> 讨论过程的完整记录另存（会话临时目录 `parallel-modules-requirements.md`），本文只留结论。

## 1. 要解决的问题

spec-guard 按能力图一个模块接一个模块推进（Spec → Plan → 任务 → 实现），同一时间只有一个当前模块。模块多、而且很多模块彼此
独立时，整体进度被串行和逐个审核拖慢。

目标：让 spec-guard 在**拆模块时**就为并行做好准备，并由一个新插件 **module-crew** 让多个会话**真实地同时**开发多个模块；
不需要并行时，一切保持现状。

不是目标：做完某个具体项目（样本项目只用于评估与第 7 关验证）；模块**内部**的任务并行（spec-guard 已有实验性的 `--dispatch`）。

## 3. 假设（ASSUMPTIONS，请逐条确认）

1. 只在**同一台 Mac** 上运行，不跨机器。
2. 第一版协调会话与模块会话**都是 Claude 桌面版**；Codex 模块会话放第二版。
3. 项目是 git 仓库，能建 worktree；用户愿意让每个模块各占一个 worktree。
4. spec-guard 已在项目里启用（约定块），能力图格式合法。
5. agent-relay 已安装可用（接口主版本 2），本机运行时有 `expectsReply`、`replyTo`、`bodyFile`、`awaitingReply` 与「等待审批」在线状态（2026-10-18 核对过运行时代码）。
6. 项目有一条能在本地跑完的完整检查命令（写在 Spec 的 Commands 一节），合并后用它判断集成是否通过。
7. 同时进行的模块上限默认 3，可配置。
8. 用户在协调会话一个窗口里审批；宿主权限弹窗仍须在原会话亲点（无法绕过）。
9. 远端合并（PR／MR）始终由用户做。
10. 预配项目工具许可能消除模块会话的大部分权限弹窗——**未验证**，第 7 关实测。
11. 宿主的「做完一轮叫醒我」在协调会话被替换后不会自动转到新会话——**未验证**；本方案不依赖它，换会话后由状态库重建。

## 4. 边界与分层

| 层 | 负责什么 | 归谁 |
|---|---|---|
| 规划层 | 是否值得并行的评估与提醒、拆分规则、模块并行边界、可开工列表与冲突、多个进行中模块的显示、并行模式开关 | **spec-guard**（只增不改，默认关闭） |
| 运行层 | 开哪几个会话、协调会话规则、公共文件变更、汇总交审、合并、恢复、失败处理 | **module-crew**（新插件） |
| 传输层 | 消息送达、请求与回复配对、唤醒、在线状态、跨宿主建会话 | **agent-relay**（必需依赖） |
| 决策收件 | 多项目统一收件、汇总用户决定 | **decision-inbox**（可选上游，第一版不接） |
| 只读复核 | 另一个 agent 审 Spec／Plan／交付 | **delegate**（可选，现有提醒） |
| 开会话、开 worktree | — | **宿主** |
| 消息协议 | 消息类型与字段、答复有效性、角色名与宿主名、等待单关单理由 | **session-protocol**（共用契约仓库） |

## 5. 规划层（spec-guard）

**开关（C0）**：`.agent/config.json` 新增 `moduleConcurrency: off|on`（名字避开 `parallel`），默认 off，经 `/spec-guard:config`
预览确认后设置。下面所有行为只在 on 时出现；off 时 spec-guard 的输出逐字不变。

- **A1 评估与提醒**：在能力图交用户评审时（主路径），以及中途接手的项目用户明确要求时评估；不在每轮注入里反复提醒。
  硬门槛：至少一波能同时开工 ≥2 个模块；有干净的集成基线。参考项：文件分区、共享接口、热点文件。结论写在交审正文里，
  形式是「建议在 Build order 加哪些逗号组、哪些模块往前挪」（关键路径与挡住的下游数只在这里算）。
- **A2 拆分**：判据是「能否独立开发」——同时进行的模块不改同一批文件；依赖已合入或接口已定。粗细是结果不是目标，能粗就粗。
  模块间的衔接默认写成上一模块追加的任务或下一模块的第一个任务（spec-guard 现有规则）；只有牵涉多个并行模块或要改不归任何模块
  的文件时才单设联调模块。「公共预置」是普通模块，放在扩张点（≥2 个模块将同时开工）之前。
- **A3 接口**：写在提供方模块的 Spec（上游规则）。扩张点前，对将同时开工的模块走 spec-guard 现有的「按需求批量前置审」，
  批准后 Spec 与 Plan 提交到集成基线，同批模块互相读得到（D18）。不建全量接口摘要文件。
- **A4 并行边界**：模块 Spec 加一节「并行边界」，按目录写独占路径（目录覆盖子孙，不用通配符）；公共文件类别：全局配置、
  锁文件、迁移、测试资源，归协调会话。越界检查复用最终验收「标出超出 Plan 预计的文件」，对比基准改为集成基线并对照并行边界；
  只报告不拦截。
- **A5 就绪与排序**：「做完」= 本地集成分支上该模块 todo 全勾；「就绪」沿用 `/map` 现有判定；先开哪个**只按 Build order**，
  取前 N 个就绪且并行边界不冲突的；逗号组保留并在 `/map` JSON 给出，串行选模块仍按书写顺序展开。
- **A6 多个进行中模块**：每个 checkout 的角色标记放 `$(git rev-parse --git-path spec-guard)/`（模块：<id>／协调），经 spec-guard
  命令预览确认后写；模块会话注入只报自己的模块，做完提示「交回协调会话」；协调会话注入改为统筹总览，不建议 `/build`；
  `/map` 只读本机其他 worktree 的 todo，标「未合入」。选当前模块与阶段计算不变。
- **规则措辞**：评审标记「`approved` 只在用户于当前对话明确批准后写入」放宽为「听到批准的会话写入」（Q6）；
  「合并永远由用户进行」改为「合并到远端分支由用户进行；并行模式下，模块合入本地集成分支可在用户批准该模块最终验收后由协调会话执行」。

**对外接口（C1）**：`/map --json` 只增字段（`schemaVersion` 仍 1）：`buildOrderGroups`、每模块 `scope`、`worktree`、顶层 `startable`
（含 `conflicts`）；`interface.json` 升 1.1，登记角色标记、越界检查、`review-mark` 三个入口。

## 6. 运行层（module-crew）

- **B1 角色**：用户、协调会话（主会话）、模块会话。星形：模块会话只和协调会话交流。协调会话职责：拆活派活、收交付、管依赖、核对、
  管集成基线与公共文件、合并、汇总交审、记批准；**不开发**、不出审查结论、不替用户决定。模块会话只做分配的模块、不改公共文件、
  不创建会话。审查者是可选外挂（第一版不做）。协调会话放 Claude 桌面版；第一版模块会话只实现 Claude，接口按宿主无关设计。
  用户主要看协调会话一个窗口，宿主权限弹窗是唯一例外（协调会话从「等待审批」在线状态发现并提醒）。
- **B2 开工**：扩张点由协调会话列出可开工模块并问一次「开这 N 个吗」；先开会话写 Spec 与 Plan，批量审批、提交到基线后才开工构建。
  每个模块一个 worktree，从本地集成分支切，分支名用模块 id；开前基线须干净。认领 = 角色标记，不建认领账本；变更请求、等待单、
  消息记录用状态库。开工说明只给任务、接口、全局约束（借鉴 Superpowers）。模块会话权限模式不高于协调会话。开会话时打开「做完一轮叫醒我」。上限默认 3。
- **B3 公共文件变更**：模块会话发【公共变更请求】；协调会话查冲突后在集成基线上单独提交，回复提交号并通知受影响模块同步。
  新增依赖、改 CI、改数据结构、互相冲突的请求交用户决定（上游 Boundaries 的 Ask first）；已批准 Spec 范围内的直接办。按到达顺序；
  完全停住时记等待单。影响已批准 Spec 时追加变更记录。
- **B4 消息**：一律 agent-relay 邮箱；请求标 `expectsReply`，回复填 `replyTo` 并首行写「回复：#N」；协调会话发出的正文由命令生成、
  走 `bodyFile`。消息类型见 session-protocol（复用 5 种，新增【交审】【公共变更请求】【协调通知】）。身份 `<项目简称>-coord`、
  `<项目简称>-<模块 id>`，`wake: "auto"`。只认协调会话转来的、带编号和原话的用户决定。被挡住必须发【等待其他会话】。
  规则放 module-crew 的 skill，不写进模块 worktree 的 CLAUDE.md。
- **B5 合并**：两层。本地层——用户批准某模块最终验收即同时授权把它合入本地集成分支，协调会话按 Build order 一次合一个，
  `git merge --no-ff`，每次合后跑完整检查；失败 `git revert -m 1` 并退回模块；冲突退回模块解决。远端层——一批合完后经用户授权推送并开一个 PR，
  由用户合并；不开 GitHub 自动合并。合并后通知下游同步、`/map` 重算；经用户同意 `git worktree remove` 收回并退役邮箱身份。
- **B6 失败与回退**：等外部条件 → `module-suspend` 挂起，不占名额；异常停点、同一 gate 再挡、改能力图，全部复用 spec-guard 现有规则；
  崩溃 → 在原 worktree 换会话；互不拖累；不设固定超时，醒来时看在线状态与待答复；用户随时可退回串行。
- **B7 宿主**：第一版处理 Claude 挂起与叫醒、权限弹窗、插件更新需新会话、钩子信任；第二版 Codex 的前置核对清单（`.git` 沙箱提权最关键、
  重启不加载、身份丢失、只能提供 skill、钩子信任、压缩后重放）。协调会话不放 Codex。

## 7. 中断、压缩、换会话后的恢复

五条原则：对话里不留唯一副本；能算就算，只存算不出来的；每次醒来从文件重建；恢复不重放；会话可替换。
状态库放 `$(git rev-parse --git-common-dir)/module-crew/`：运行配置、会话登记、待用户决定事项与原话、变更请求、等待单、发出的正文、只追加的事件日志。
module-crew 自带钩子在启动／恢复／压缩及每轮按角色注入；只读命令 `status` 随时重建全貌。换会话需用户同意 `takeover` 邮箱名一次。

## 8. 共用契约 session-protocol

独立小仓库，只放协议文档（带版本）、每种消息的标准样例、一致性测试；不放代码。各插件钉住一个版本、在自己测试里跑样例。
先改契约再改实现；改动经用户批准，各插件负责人都可提。v1 由 decision-inbox 现有 `spec/message-protocol.md` 与样例迁入，
module-crew 的三种新消息作为 v1.1。

## 9. 防线（上次失败的教训）

spec-guard 0.12.0（2026-09-13）曾整体退役一套并行工作流：没想好就动手、越做越复杂、改动面太大、对既有实现不熟、做的是任务级并行。
- L1 先定需求再动手（七关）。
- L2 spec-guard 只改有限几处：开关、评估提醒、并行边界与越界对照、`/map` 新字段、角色标记与按角色注入、其他 worktree 进度、规则措辞；
  默认关闭，关闭时逐字不变（回归测试证明）。不在 spec-guard 放任何运行时。
- L3 保留 `scripts/check-no-parallel-surface.py`；新内容不用 `parallel-` 命名。
- L4 借鉴退役设计的语义，不照搬其严格度。
- L5 先做最小版本，第 7 关证明有效再扩；出现「要改阶段判断核心」「要在 spec-guard 里管会话」就停下复盘。

## 14. 一个协调会话管所有派活（2026-10-22 用户确认）

**要解决的问题**：插件只覆盖多模块并行，单个需求、单个 bug 只能用原生关联会话做，提交不经合并队列、不通知在开发的模块同步，两套规则管同一条集成分支。

**目标**：每个项目可有一个常驻的协调会话，所有派活都经它——单需求与 bug 走轻流程，多模块并行走现有流程；改动只从合并队列一个入口进集成分支。
**成功标准**：2 个模块在开发时来一个 bug——bug 开第三个会话修、不打断模块；修完用户点批准合入；两个模块收到同步通知；协调会话压缩或清空后手上的活一件不丢。
**硬约束**：不影响正在进行的开发；插件按会话开关，没升级的会话一切照常。

1. **开关**：装了不等于开了；用户明说升级后该会话才进入协调流程。一个 git 仓库（含所有 worktree）最多一个协调会话，第二个被拦；旧的不在了由用户明说接管（`takeover`）。项目里没有协调会话时插件完全安静；只在用户说到派活、并行这类话或直接用 module-crew 命令时提一句可以升级。
2. **绕开协调的会话**：不拦，提醒一次。有协调会话时，普通会话在第一次回复里顺带说明「本项目已有协调会话（目录、分支），派活与合入一般由它统一安排；在这里直接改也行，只是不经合并队列；要交给它的话我把事情整理成一段话你贴过去」，之后照用户意图做、不再重复。协调会话下一次回复时告诉用户「<目录> 里有一个没登记的会话在本项目活动」；发现不经队列合入的提交时照常通知各模块同步。
3. **轻任务验收**：做事的会话测试全过才交回，附测试命令与结果、实际改的文件、与任务单预计是否一致；合并时协调会话后台再跑完整检查；用户看简短说明点批准。bug 必须先补复现测试，需求不强制。
4. **升级前提**：同 `module-crew start` 的体检——git 仓库、集成基线干净、spec-guard 与 agent-relay 已装且接口版本够用、项目已启用 spec-guard（`.agent/config.json`）。轻任务会话与模块会话一样走 agent-relay 与协议消息。
5. **能力图**：升级时不要求；开模块时才检查。轻任务不调 spec-guard、不写 Spec。
6. **合入后出问题**：默认往前修，另开 bug 任务；问题挡住在开发的模块时才提议回滚，用户点头后按轻任务 `git revert` 走队列。任务记录记下「由哪个任务带进来」。
7. **常驻多久**：靠 spec-guard 的提醒，由用户手动压缩或清空，插件不设阈值。压缩后会话编号不变；**清空后编号会变**（见下方实测），协调身份要能接上，活从状态库重建。
8. **名额**：多模块并行默认上限改为 2（原 3；已开工项目不变）；轻任务不设总数上限，预计改的文件与在做的活重叠就排队；bug 优先合入，不打断正在合的那一件。
9. **做大了**：做事的会话停下交回升格请求（做了什么、剩什么、为什么超范围），代码留在自己分支；用户选升格（占一个模块名额）、缩小或取消。只多改了没人在碰的文件，交回时报一句即可。
10. **长命令**：合并时的完整检查等长命令改后台运行，协调会话照常回话；写代码的活才交给关联会话。
11. **宿主限制**：被别的会话消息唤醒的一轮开不了会话，只出卡片等用户点；插件不绕过，只保证卡片里的任务单写全。

**这一版不做**：派给 Codex；自动处理权限弹窗；拦截没升级的会话；管没装插件时的原生用法；自动回滚；自动升格。

**实测（2026-10-22，Claude Code CLI，临时仓库挂记录钩子）**：对一个会话执行 `/clear`，钩子依次收到 `SessionEnd`（旧编号，`reason: "clear"`）与 `SessionStart`（**新编号**，`source: "clear"`，同一 `cwd`），钩子环境里的 `CLAUDE_CODE_SESSION_ID` 也换成新编号；新会话的载荷里没有旧编号。压缩与 `--resume` 编号不变（此前实测）。桌面版的清空未单独实测。
